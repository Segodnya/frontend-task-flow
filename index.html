От постановки до мержа с Claude Code

Ты ставишь задачу и принимаешь решения, а Claude Code пишет код, проверяет его и готовит MR к аудиту.

Начать Шпаргалка

Агент пишет код быстрее нас, но результат сильно зависит от того, как с ним работать. Один разработчик получает аккуратный MR с первого раза, другой проходит несколько кругов аудита на ту же задачу. Мы попробовали разные подходы на реальных задачах и собрали в один процесс то, что сработало.

    Весь путь коротко

    Цель у процесса простая: меньше кругов аудита и одинаково понятные MR. Все открытые вопросы по задаче мы закрываем до первой строчки кода: как должна работать фича, какой вариант UX выбрать, что вернёт бэкенд. А всё, что может найти машина, она находит до аудитора. Поэтому аудитор получает MR в одном и том же виде от любого разработчика.

    Процесс обязательный, как стек проекта: аудиторы и тестировщики рассчитывают, что задача прошла именно эти шаги и MR пришёл в привычном виде. Зато придумывать ничего не нужно. На каждом шаге написано, что делать, какую команду запустить, зачем она нужна и как понять, что шаг закончен. Если нашёл приём лучше, пробуй и приноси, обновим флоу для всех.

    В основе лежат скиллы Мэтта Покока. Своё мы добавили только там, где их не хватает: самопроверка MR перед аудитом и работа с Jira и GitLab. Почему не Superpowers, OpenSpec или Spec Kit – в сравнении.

    Четыре принципа

    Если какой-то шаг кажется лишним, загляни сюда: скорее всего, он нужен ради одного из этих принципов.

    Всё важное – в файлах, а не в чате

    Решения живут в task.md, спеке и тикетах. Поэтому любую сессию можно закрыть и начать заново без потерь.

    Один тикет – один MR

    Такой MR аудитор читает за один подход. Тикет – тонкий срез фичи, который проверяется сам по себе («Трассирующие тикеты»).

    Слова агента – гипотеза

    «Готово», «тесты прошли», «так и было» мы принимаем только вместе с командой и её выводом. Строка «4 passed» в ответе агента – тоже только слова.

    Автор и ревьюер – разные сессии

    Ревьюер со свежим контекстом не защищает код, который написал сам («Писатель и рецензент»).

    Настройка

    Ты

    один раз на репозиторий

    setup.sh
    Скрипт

    ставит плагины и настройки Claude Code. После этого агент сам ходит в Jira и GitLab и открывает стенд в браузере

    Настройку делают один раз в каждом репозитории, где ты работаешь, и занимает она минут 15. Скрипт ставит плагины и настройки Claude Code только для этого репозитория. Глобально он делает три вещи:

    1. ставит через Homebrew три CLI: jq, glab, jira-cli;
    2. добавляет один блок с правилами агента в ~/.claude/CLAUDE.md;
    3. включает auto mode в ~/.claude/settings.json. Claude Code читает этот режим только из пользовательских настроек. Если ты уже выбрал свой режим, скрипт его не меняет.

    Всё остальное в этих файлах остаётся как есть.

    1. Склонируй репозиторий флоу: 
      git clone https://github.com/Segodnya/frontend-task-flow.git ~/frontend-task-flow
    2. Перейди в репозиторий, в котором будешь работать: 
      cd ~/work/<репозиторий>
    3. Запусти скрипт настройки, передав адрес своей Jira и хост своего GitLab. Без этих аргументов скрипт остановится с ошибкой: 
      bash ~/frontend-task-flow/setup.sh --jira https://<компания>.atlassian.net --gitlab gitlab.<компания>.com

    После этого агент сможет сам ходить в Jira и GitLab из терминала, открывать стенд в браузере и сравнивать его с макетом. В репозитории появятся скиллы Мэтта Покока и наши скиллы самопроверки. Коммитить ничего не нужно: плагины и настройки записываются в .claude/settings.local.json, а все файлы скрипта скрыты от git и в git status не появятся.

    Запускать скрипт повторно безопасно: твои настройки он не перезаписывает. Поэтому обновить флоу просто: сделай git pull в ~/frontend-task-flow и запусти скрипт ещё раз с теми же аргументами.

    Windows: работай в WSL (Ubuntu) и поставь туда Homebrew. Для браузерных проверок агенту понадобится Chrome внутри WSL. Если какой-то шаг скрипта упал, выполни его команды вручную: они лежат в setup.sh, шаги пронумерованы от 1/6 до 6/6, как в таблице ниже.

    Если в репозитории нет файла docs/agents/issue-tracker.md, значит, его ещё не подключили к флоу. Тогда сначала пройди Настройку нового репозитория: её делают один раз на всю команду.

    Готово, когда: в репозитории claude → /skills показывает mattpocock-skills:grill-with-docs и segodnya-agents:mr-ready, а /mcp – chrome-devtools ✔ connected.

    Понять задачу

    Ты

    пишешь task.md, отвечаешь на вопросы агента

    /grill-with-docs
    Агент

    изучает код через субагентов, задаёт вопросы раундами по 5–7 штук и сразу записывает решения в файлы

    Если агент понял задачу не так, как ты, он уверенно сделает не то, и выяснится это только на аудите. Поэтому до кода мы проговариваем задачу с агентом, пока у него не кончатся вопросы. Этот разговор называется grill: агент изучает код, задаёт вопросы и сразу записывает решения в файлы. У Мокевнина этот приём описан в главе «Гриллинг».

    Если правка крошечная, разговор не нужен: просто попроси агента и посмотри на дифф. Всё остальное начинается с grill:

    1. Собери папку фичи в specs и напиши task.md на 10–20 строк: что делаем, зачем и в каких репозиториях.
    2. Открой новую сессию в корне репозитория проекта и запусти /mattpocock-skills:grill-with-docs с промптом ниже.
    3. Отвечай на вопросы агента, пока они не кончатся. Обычно это несколько раундов по 5–7 вопросов.
    /mattpocock-skills:grill-with-docs Разрабатываем PROJ-100 — выбор цвета кнопки на странице бронирования. План в task.md, макеты в images. Изучи код через субагентов, задай вопросы, чтобы полностью понять задачу. CONTEXT.md и ADR пиши в папку фичи. @specs/<путь фичи>/task.md

    PROJ-100. Агент спросил, давать ли клиенту любой цвет или только палитру. Ты выбрал палитру из дизайн-системы: на произвольном цвете текст кнопки может стать нечитаемым. Агент записал это решение в ADR-0001, а в CONTEXT.md добавил термины «акцентный цвет» и «палитра».

    Готово, когда: в task.md не осталось открытых вопросов к тебе, CONTEXT.md создан.

    One shot, grill или wayfinder

    Grill нужен, чтобы агент не построил не то. Если переделать дёшево, этот риск ничего не стоит: проще посмотреть на дифф и поправить. Поэтому мелкие правки мы делаем сразу, а всё остальное начинаем с /grill-with-docs.

    /wayfinder нужен для больших задач с высокой неопределённостью, которые не помещаются в одну сессию. Даже такую задачу лучше начинать с grill: часто она оказывается проще, чем казалась, и карта с тикетами решений не понадобится. Но если grill расползается (вопросы не кончаются, тумана больше, чем ждали), скажи агенту:

    /mattpocock-skills:wayfinder давай превратим это в карту

    Он соберёт из разговора карту решений, и дальше вы пройдёте её по одному вопросу за раз.

    Папка фичи и task.md

    Постановка хранится в общем репозитории спецификаций. Он подключён сабмодулем specs в репозиторий проекта. Код фичи может лежать и в других репозиториях: их мы называем репозиториями кода. Часто это один и тот же репозиторий. Папку фичи заводи по структуре из README репозитория спецификаций:

    specs/<группа>/<репозиторий>/frontend/<namespace>/<feature>/
├── task.md            # пишешь ты: что и зачем
├── CONTEXT.md         # глоссарий – появится после grill (в скиллах 1.3+ – GLOSSARY.md)
├── images/*.png       # скриншоты макетов
└── docs/
    ├── prd.md         # PRD продукта: зачем фича и для кого
    ├── backend/*.md   # НТЗ бэкенда – контракт API
    └── adr/           # решения с причинами – появятся после grill

    Положи в папку всё, что у тебя есть: PRD, НТЗ бэкенда, макеты. Чем больше агент прочитает сам, тем меньше вопросов задаст тебе.

    task.md пишешь ты, хватит 10–20 строк. В нём нужны три вещи:

    1. что сделать и зачем;
    2. с чем работаем: локальные пути к репозиториям (@~/work/<репозиторий>/frontend/…), а не ссылки на GitLab: по путям агент читает код сам;
    3. последней строкой: «исследование поручи субагентам, чтобы оставить основной контекст чистым».
    Что будет в сессии grill

    Открой новую сессию в корне репозитория проекта, чтобы агенту были видны и код, и specs. Сначала агент несколько минут изучает код через субагентов, так что не пугайся тишины. Потом он задаёт вопросы раундами по 5–7 штук и к каждому предлагает свою рекомендацию. Отвечай одним сообщением на весь раунд. Решения агент сразу записывает в файлы, поэтому к концу разговора у тебя будет task.md без открытых вопросов и глоссарий CONTEXT.md. На решения, которые трудно отменить и неочевидно объяснить, агент предложит ADR.

    Рекомендацию агента тоже проверяй: это гипотеза. На одной реальной задаче разработчик отклонил 5 рекомендаций из 24 и ещё 2 поправил.

    Если вопрос не к тебе, а к бэкенду или дизайнеру, агент вынесет его в task.md, в секцию по адресату. Когда получишь ответ, вставь его в файл и продолжай в новой сессии. А если разговор ушёл не туда, скажи:

    Стой. Запиши всё, что решили, в план.

    Решённый вопрос в task.md выглядит так: ~~iframe или вёрстка?~~ **решено:** вёрстка [ADR-0001].

    Разбить на тикеты

    Ты

    проверяешь декомпозицию

    /to-spec → /to-tickets
    Агент

    собирает спеку, режет её на вертикальные срезы и после твоего «ок» заводит тикеты в Jira

    Когда вопросы кончились, задачу нужно декомпозировать, и всегда до начала кода. Маленький тикет – это маленький MR: аудитор прочитает его за один подход, а тестировщику проще проверить небольшую правку. Разрезать мелко получается не всегда, но мы к этому стремимся.

    Делай это в той же сессии, где был grill: весь контекст разговора уже у агента, и ему ничего не придётся вспоминать.

    1. Спека

    /mattpocock-skills:to-spec

    Агент соберёт из разговора спеку: проблема, решение, user stories, принятые решения, как тестировать. Нового интервью не будет: агент только сверит с тобой, на каких границах модулей проверять фичу тестами. Спека публикуется комментарием в PROJ-100.

    2. Тикеты

    Чтобы агент сразу заполнил поля Jira, запусти to-tickets так:

    /mattpocock-skills:to-tickets Заведи тикеты дочерними к PROJ-100. Проставь связи «Блокирует» по графу. Поля: Проект — <проект>, Гильдия — Frontend, assign на меня.

    Агент разрежет спеку на вертикальные срезы: каждый проходит через все слои, проверяется сам по себе и помещается в одну сессию. Он покажет список: проверь размер тикетов и связи между ними. Иногда даже один срез – это несколько тысяч строк. Тогда сначала попроси срез потоньше: например, сперва один цвет по умолчанию, потом палитра. После твоего «ок» агент заведёт тикеты в Jira.

    PROJ-100. Агент предложил три среза. PROJ-101: кнопка на странице бронирования берёт акцентный цвет из настроек. PROJ-102: текст кнопки читается на любом цвете палитры. PROJ-103: клиент выбирает цвет из палитры в настройках. PROJ-101 блокирует два других.

    Готово, когда: все тикеты в Jira, связи «Блокирует» проставлены.

    Промпт для крупного тикета

    Если какой-то тикет выглядит крупным, попроси разрезать его:

    В PROJ-103 будет много кода, аудитору тяжело читать. Найди через субагентов срезы потоньше, каждый со своим видимым результатом. Если тонко не режется, предложи стопку по слоям, где у каждого MR уже есть потребитель.

    Разрез по слоям (API, модель, UI) – запасной вариант. Слой без потребителя аудитор не сможет оценить, а линтер мёртвого кода упадёт. Подробнее о стопке – в Нарезке ветки на MR.

    3

    Написать код

    Ты

    по сессии на тикет

    /implement
    Агент

    пишет код, гоняет проверки и сравнивает стенд с макетом

    На каждый тикет мы открываем новую сессию в репозитории кода: так агент начинает с чистого контекста и думает только об этом тикете.

    /mattpocock-skills:implement Работаем над PROJ-103 (клиент выбирает цвет из палитры). Спека — в PROJ-100. Сначала перечитай тикет, спеку и макеты, задай вопросы. До правок прогони линтер и тесты, чтобы отличать свои ошибки от старых. Исследование и независимые блоки — субагентам. В конце открой стенд и сверь его с макетами.

    Фразу «сначала задай вопросы» не пропускай. Без неё скилл сразу начинает писать код, и ты не успеешь поправить его понимание задачи. Остальные фразы промпта тоже нужны: сам скилл не делает baseline и не открывает стенд.

    Дальше агент работает сам. От тебя нужно ответить на его вопросы и посмотреть на результат.

    PROJ-103. Агент спросил, сохранять цвет сразу при выборе или по кнопке «Сохранить», как остальные настройки. Ты выбрал кнопку. В конце агент показал вывод tsc, eslint, jest и скриншот стенда рядом с макетом.

    Готово, когда: проверки зелёные, скриншот стенда совпадает с макетом, агент показал команды и их вывод.

    Что делает агент

    Скилл даёт каркас: проверки по ходу работы и ревью в конце. Остальное добавляет наш промпт.

    1. Запускает линтер и тесты до правок, чтобы отличать свои ошибки от старых.
    2. Пишет код, независимые части – параллельными субагентами.
    3. Гоняет tsc, eslint, jest по своим файлам, пока всё не станет зелёным.
    4. Открывает стенд и сравнивает скриншот с макетом.
    5. В конце проводит ревью своей работы через /code-review.

    Что проверить нельзя (прод-сборка, CDN), агент помечает «не проверено». Если слышишь «должно работать», переспроси.

    Коммит

    Скилл велит агенту закоммитить работу, но коммит делаешь ты: наше правило агента сильнее шага скилла. Перед коммитом посмотри git status: правило записано текстом, а не запретом в настройках, и агент может его нарушить.

    Баг на стенде

    Если на стенде нашёлся баг, запусти скилл диагностики. Агент воспроизведёт баг, найдёт причину и только потом начнёт чинить:

    /mattpocock-skills:diagnosing-bugs <что сломано>

    Если нужен живой цикл в браузере с отладочными логами:

    /segodnya-agents:local-debug @<файл> <что сломано>
    4

    Самопроверка

    Ты

    коммит, Draft MR

    /checklist-deploy → /mr-ready
    Агент

    свежий ревьюер ищет всё, что может найти машина, а другой агент это чинит, коммитит и пушит

    Перед аудитом MR проходит самопроверку: свежий агент-ревьюер ищет всё, что может найти машина, а другой агент это чинит. Так аудитор получает MR, в котором машинные замечания уже закрыты.

    1. Закоммить, запушь и создай Draft MR. База MR – ветка, от которой ответвилась ветка задачи.
    2. Собери чек-лист перед отгрузкой по диффу от базы MR:

    3. Открой новую сессию в репозитории кода и запусти самопроверку. Отправь два сообщения: сначала цель, потом скилл. Цель не даёт сессии остановиться посреди цикла. 
      /goal mr-ready выдал финальный отчёт по MR. Чек-лист отгрузки: <адрес Jira>/browse/PROJ-103?focusedCommentId=<id>
      /segodnya-agents:mr-ready

    Пока mr-ready работает, от тебя почти ничего не нужно. Скилл спросит тебя, только если упрётся в продуктовую развилку: два варианта UX или неясный контракт бэкенда.

    PROJ-103. Ревьюер нашёл, что пустое значение цвета ломает кнопку. Фиксер добавил цвет по умолчанию, запушил коммит и ответил в тред его хэшем. Во втором раунде находок не было, и отчёт пришёл со статусом ready.

    Готово, когда: отчёт mr-ready – ready, CI зелёный. Если отчёт stuck или cap, прочитай в нём блок «Открыто для ревьюера» и реши сам.

    Что делает mr-ready

    Свежий ревьюер ищет проблемы в диффе и сверяет его с чек-листом. Каждую находку он оставляет тредом на нужной строке MR. Другой агент чинит её или отвечает, почему править не нужно, потом коммитит и пушит. Круг повторяется, пока находки не кончатся.

    mr-ready – единственный скилл, которому наши правила разрешают коммитить, пушить и писать в MR без отдельной просьбы. --force, --amend, rebase и закрытие тредов ему запрещены.

    Ревьюер и фиксер – разные субагенты, и на каждом раунде они свежие. Правка уходит коммитом с ответом в тред, отказ – ответом с обоснованием. Треды закрывает аудитор, а не агент. Если ревьюер нашёл дефект не из диффа задачи, он попадёт в отчёт черновиком тикета.

    Вопросы скилл задаёт в двух случаях: пакетом в начале, если чего-то не нашёл (чек-лист, команды проверок), и на продуктовой развилке.

    Нарезка готовой ветки на MR

    Иногда декомпозиция не удаётся, и вся фича вырастает в одной большой ветке. Это аварийный выход: в следующий раз режь задачу на шаге 2. Но если так уже случилось, ветку можно аккуратно разрезать на несколько MR.

    Как нарезать ветку на несколько MR

    Наша цель – превратить проверенную ветку в несколько небольших MR без конфликтов и без потери правок. Потом каждый MR проходит шаг 4.

    1. План нарезки

    Предложи агенту темы и попроси проверить зависимости:

    Дифф ветки большой. Предлагаю разделить на N MR: <тема 1> / <тема 2> / <тема 3>. Посмотри зависимости по импортам: стопкой или независимо от master? Будут ли конфликты?

    Агент выберет одну из двух форм. Независимые MR ответвляются каждый от master (или от базовой ветки фичи) и мержатся в любом порядке. Так можно, только если части не импортируют друг друга. В стопке каждый MR целится в ветку предыдущего. Она подходит для общего фундамента: рефакторинг без изменения поведения → данные → UI. Стопку мержат снизу вверх, без squash, и после мержа GitLab сам перенацеливает следующий MR.

    Внизу стопки не должно быть кода без потребителей, например схемы или хука, которые никто не вызывает. Аудитор не поймёт, зачем они, а линтер мёртвого кода упадёт. В таком случае лучше сделать MR побольше.

    2. Нарезка

    Теперь попроси агента разнести правки по веткам:

    Заведи тикеты под новые MR дочерними к PROJ-100. Разнеси правки по веткам через субагентов, каждого — в отдельном worktree. Проверь каждую ветку (tsc, eslint, тесты, e2e), закоммить, запушь, создай MR. Потом сверь: верхняя ветка побайтово равна исходной.

    Ветки собираются из итогового состояния файлов, а не нарезкой истории коммитов, поэтому конфликтов нет. В конце обязательно проверь сверку: команда ниже должна вывести пустой дифф. Если он не пустой, какая-то правка потерялась или задвоилась.

    git diff <исходная ветка> <верх стопки>

    Здесь агент коммитит и пушит сам: ты явно разрешаешь это на время нарезки.

    3. Чек-листы

    Осталось собрать чек-листы:

    Для каждого тикета — /checklist-deploy по диффу его MR, опубликуй в тикет в jira wiki-разметке. Общий чек-лист для тестировщика по всей фиче — в PROJ-100.

    В чек-листе тикета – только кейсы его диффа и порядок мержа в «Особенностях отгрузки». Общий чек-лист описывает сквозные сценарии: по нему тестировщик проверяет фичу целиком, когда смержены все MR.

    Дальше запусти /segodnya-agents:mr-ready по каждому MR, снизу стопки вверх.

    Готово, когда: все MR зелёные в CI и без конфликтов, сверка пустая, чек-листы опубликованы.

    Как беречь контекст

    Контекст агента ограничен. В длинной сессии модель хуже использует то, что было давно (context rot). Окно в 1M токенов откладывает сжатие, но эту проблему не снимает. Поэтому мы храним всё там, откуда агент возьмёт это сам, когда понадобится. В этом помогают пять привычек:

    Разведку отдавай субагентам

    Они читают много файлов, а в основную сессию возвращают только вывод.

    /clear, а не /compact

    …когда всё решённое уже в файлах. Сводка от /compact теряет детали, а чистая сессия с хорошим промптом почти всегда работает лучше длинной. /compact нужен, только если остались незаписанные решения.

    Уходишь – оставь handoff

    /mattpocock-skills:handoff: цель, решения и причины, что пробовали и отбросили, следующий шаг. Записка ложится во временную папку и ссылается на task.md и тикеты, а не копирует их.

    Не раздувай CLAUDE.md

    Правило, которое агент соблюдает и без него, лишнее («Раздутая память»). CLAUDE.md направляет агента, но не гарантирует соблюдения. Критичный запрет задаётся через permissions.deny или хук («Исполняемые ограничения»).

    Дай агенту способ проверить себя

    Тест, линтер, скриншот рядом с макетом. Доказательство приходит из окружения, а не из рассказа агента («Петля обратной связи»). Иначе агент объявит преждевременный успех.

    Почему скиллы Мэтта

    Готовых флоу для агентов много. Мы сравнили пять вариантов и выбрали тот, где меньше всего церемоний на типичную фронтовую задачу.

    ФлоуКак устроенЧто остаётся после задачиЦена для нас
    Скиллы Мэтта Пококаодин короткий скилл на шаг: grill → спека → тикеты → код → ревьютикеты в трекере, глоссарий, редкие ADRсвои скиллы нужны для самопроверки MR и Jira
    Superpowersстрогий конвейер: брейншторм → дизайн-док → план из задач по 2–5 минут → субагенты, обязательный TDDдизайн-док и план на каждую фичумного церемоний для правки на сотню строк; код, написанный до теста, скилл удаляет
    OpenSpecна каждое изменение: предложение → задачи → реализация → архивproposal.md, design.md, tasks.md и дельты спеквторой источник правды рядом с arc/specs и Jira
    Spec Kitspec-driven development: конституция проекта → спека → план → задачи → реализациябольше всего документов на фичудокументы надо писать, читать и держать в актуальном виде
    Свой набор скилловвсё под насчто решим самиошибки ищем и чиним только мы, новичку нечего почитать снаружи

    Мы выбрали скиллы Мэтта по трём причинам:

    1. Один шаг – один скилл, а скилл читается за минуту. Например, implement занимает несколько строк. Когда агент делает что-то странное, причину легко найти.
    2. В скиллы заложены разговор до кода, вертикальные срезы и ревьюер в отдельной сессии. Те же приёмы описывают книга Мокевнина и best practices Anthropic.
    3. Проект живой: около 290 тыс. звёзд и 24 тыс. форков на GitHub, релизы раз в несколько недель. Обновление приходит через плагин, повторный запуск setup.sh ничего не ломает.

    Скиллы Мэтта пишет в основном один автор: у репозитория 8 контрибьюторов. Поэтому скиллы согласованы друг с другом. Если важно большое сообщество разработчиков, у Spec Kit их 318, у OpenSpec 145, у Superpowers 44. Зато там и документов на задачу больше. Данные GitHub на 15 октября 2026.

    Глоссарий

    Если в тексте встретилось незнакомое слово (агент, сессия, grill, спека, тред), загляни сюда. Термины с пунктирным подчёркиванием в тексте показывают подсказку при наведении.

    Агент
    Claude Code: читает и изменяет код, запускает команды.
    Сессия
    Один разговор с агентом. Новая сессия ничего не помнит о предыдущей, кроме файлов.
    Контекст (окно)
    Всё, что агент видит в сессии: инструкции, диалог, прочитанные файлы. Ограничен. См. Как беречь контекст.
    Субагент
    Агент, которого основная сессия запускает на подзадачу. У него свой контекст, назад он возвращает только вывод.
    Скилл
    Упакованная инструкция под конкретную задачу. Вызывается командой /имя.
    MCP
    Способ подключить к агенту внешний инструмент, например браузер.
    CLAUDE.md
    Файл правил, который агент читает в начале каждой сессии: личный ~/.claude/CLAUDE.md и командный в репозитории.
    One shot
    Агент делает задачу сразу, без предварительного разговора. Подходит для крошечного диффа.
    Grill
    Режим, в котором агент задаёт вопросы, пока не поймёт задачу полностью.
    Wayfinder
    Карта решений для задачи, которая не помещается в одну сессию. Каждый вопрос – отдельный тикет, их решают по одному.
    Спека
    Итог grill одним документом: проблема, решение, user stories, решения, тесты.
    Вертикальный срез
    Тикет, который проходит через все слои (данные, API, UI, тесты) и проверяется сам по себе. Противоположность – тикет «только API» или «только вёрстка».
    ADR
    Короткая запись архитектурного решения: контекст, решение, причины, последствия.
    Дифф / staged
    Изменения в коде / изменения, добавленные в индекс git (git add).
    MR
    Merge request в GitLab. Тред – обсуждение на строке MR.
    Аудитор
