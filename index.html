    The whole path in brief

    The goal of the process is simple: fewer review rounds and MRs that are equally easy to read. We close every open question about the task before the first line of code: how the feature should work, which UX option to pick, what the backend returns. And everything a machine can find, it finds before the reviewer does. So the reviewer gets the MR in the same shape from any developer.

    The process is mandatory, like the project stack: reviewers and QA count on the task having gone through exactly these steps and the MR arriving in the familiar shape. The upside is that you don't have to invent anything. Each step says what to do, which command to run, why it's needed and how to tell the step is done. If you find a better technique, try it and bring it back, and we'll update the flow for everyone.

    The foundation is Matt Pocock's skills. We added our own only where they fall short: MR self-review before human review, and working with Jira and GitLab. Why not Superpowers, OpenSpec or Spec Kit is covered in the comparison.

    Four principles

    If a step looks unnecessary, look here: most likely it exists for one of these principles.

    Everything important lives in files, not in the chat

    Decisions live in task.md, the spec and the tickets. So any session can be closed and started over without losing anything.

    One ticket, one MR

    A reviewer reads such an MR in one sitting. A ticket is a thin slice of the feature that can be verified on its own (“Tracer bullet tickets”).

    The agent's words are a hypothesis

    “Done”, “tests pass”, “it was like that before” we accept only together with the command and its output. The line “4 passed” in the agent's reply is also just words.

    Author and reviewer are different sessions

    A reviewer with a fresh context doesn't defend code it wrote itself (“Writer and reviewer”).

    Setup

    You

    once per repository

    setup.sh
    Script

    installs Claude Code plugins and settings. After that the agent goes to Jira and GitLab on its own and opens the app in the browser

    Setup is done once in every repository you work in, and it takes about 15 minutes. The script installs Claude Code plugins and settings for this repository only. Globally it does three things:

    1. installs three CLIs via Homebrew: jq, glab, jira-cli;
    2. adds one block of agent rules to ~/.claude/CLAUDE.md;
    3. enables auto mode in ~/.claude/settings.json. Claude Code reads this mode from user settings only. If you've already picked your own mode, the script leaves it alone.

    Everything else in those files stays as it is.

    1. Clone the flow repository: 
      git clone https://github.com/Segodnya/frontend-task-flow.git ~/frontend-task-flow
    2. Go to the repository you'll be working in: 
      cd ~/work/<repository>
    3. Run the setup script, passing your Jira address and your GitLab host. Without these arguments the script stops with an error. It also needs Homebrew, Node.js and Claude Code installed and stops with a hint if one is missing: 
      bash ~/frontend-task-flow/setup.sh --jira https://<company>.atlassian.net --gitlab gitlab.<company>.com

    After that the agent can go to Jira and GitLab from the terminal on its own, open the app in the browser and compare it with the mockup. Matt Pocock's skills and our self-review skills appear in the repository. Nothing needs to be committed: plugins and settings go to .claude/settings.local.json, and all the script's files are hidden from git and won't show up in git status.

    Running the script again is safe: it doesn't overwrite your settings. So updating the flow is easy: git pull in ~/frontend-task-flow and run the script again with the same arguments.

    Windows: work in WSL (Ubuntu) and install Homebrew there. For browser checks the agent needs Chrome inside WSL. If a script step fails, run its commands by hand: they're in setup.sh, the steps are numbered 1/6 to 6/6, as in the table below.

    If the repository has no docs/agents/issue-tracker.md file, it hasn't been connected to the flow yet. In that case go through New repository setup first: it's done once for the whole team.

    Done when: in the repository claude → /skills shows mattpocock-skills:grill-with-docs and segodnya-agents:mr-ready, and /mcp shows chrome-devtools ✔ connected.

    Understand the task

    You

    write task.md, answer the agent's questions

    /grill-with-docs
    Agent

    explores the code with subagents, asks questions in rounds of 5–7 and writes the decisions to files right away

    If the agent understood the task differently from you, it will confidently build the wrong thing, and that comes out only at review. So before any code we talk the task through with the agent until it runs out of questions. This conversation is called a grill: the agent explores the code, asks questions and writes the decisions to files right away. Mokevnin describes this technique in the chapter “Grilling”.

    If the change is tiny, no conversation is needed: just ask the agent and look at the diff. Everything else starts with a grill:

    1. Set up the feature folder in specs and write a 10–20 line task.md: what we're doing, why, and in which repositories.
    2. Open a new session in the project repository root and run /mattpocock-skills:grill-with-docs with the prompt below.
    3. Answer the agent's questions until they run out. Usually that's several rounds of 5–7 questions.
    /mattpocock-skills:grill-with-docs We're building PROJ-100 — picking the button color on the booking page. The plan is in task.md, the mockups are in images. Explore the code with subagents, ask questions until you fully understand the task. Write GLOSSARY.md and ADRs to the feature folder. @specs/<feature path>/task.md

    PROJ-100. The agent asked whether to let the client pick any color or only a palette. You chose a palette from the design system: on an arbitrary color the button text may become unreadable. The agent recorded this decision in ADR-0001 and added the terms “accent color” and “palette” to GLOSSARY.md.

    Done when: task.md has no open questions left for you, GLOSSARY.md is created.

    One shot, grill or wayfinder

    A grill exists so the agent doesn't build the wrong thing. If redoing is cheap, that risk costs nothing: it's easier to look at the diff and fix it. So we do small changes right away, and start everything else with /grill-with-docs.

    /wayfinder is for big tasks with high uncertainty that don't fit in one session. Even such a task is better started with a grill: it often turns out simpler than it looked, and a map with decision tickets won't be needed. But if the grill sprawls (the questions don't end, there's more fog than expected), tell the agent:

    /mattpocock-skills:wayfinder let's turn this into a map

    It will build a decision map from the conversation, and from there you'll go through it one question at a time.

    The feature folder and task.md

    The brief lives in the shared specifications repository. It's attached as the specs submodule in the project repository. The feature's code can also live in other repositories: we call those code repositories. Often it's the same repository. Create the feature folder following the structure from the specifications repository README:

    specs/<group>/<repository>/frontend/<namespace>/<feature>/
├── task.md            # you write it: what and why
├── GLOSSARY.md        # glossary – appears after the grill (CONTEXT.md in skills before 1.3)
├── images/*.png       # mockup screenshots
└── docs/
    ├── prd.md         # product PRD: why the feature and for whom
    ├── backend/*.md   # backend tech spec – the API contract
    └── adr/           # decisions with reasons – appear after the grill

    Put everything you have in the folder: PRD, backend tech spec, mockups. The more the agent reads on its own, the fewer questions it asks you.

    You write task.md, 10–20 lines is enough. It needs three things:

    1. what to do and why;
    2. what we work with: local paths to the repositories (@~/work/<repository>/frontend/…), not GitLab links: the agent reads the code itself by path;
    3. as the last line: “delegate research to subagents to keep the main context clean”.
    What happens in a grill session

    Open a new session in the project repository root so the agent can see both the code and specs. First the agent spends a few minutes exploring the code with subagents, so don't be alarmed by the silence. Then it asks questions in rounds of 5–7 and offers its own recommendation for each. Reply to the whole round in one message. The agent writes the decisions to files right away, so by the end of the conversation you'll have a task.md with no open questions and a GLOSSARY.md glossary. For decisions that are hard to undo and not obvious to explain, the agent will suggest an ADR.

    Check the agent's recommendations too: they're hypotheses. On one real task a developer rejected 5 recommendations out of 24 and corrected 2 more.

    If a question is not for you but for the backend or the designer, the agent puts it in task.md, in the section for that addressee. When you get the answer, paste it into the file and continue in a new session. And if the conversation goes off track, say:

    Stop. Write everything we've decided into the plan.

    A resolved question in task.md looks like this: ~~iframe or markup?~~ **decided:** markup [ADR-0001].

    2

    Split into tickets

    You

    check the decomposition

    /to-spec → /to-tickets
    Agent

    assembles the spec, cuts it into vertical slices and, after your “ok”, creates the tickets in Jira

    When the questions have run out, the task needs to be decomposed, and always before the code starts. A small ticket is a small MR: the reviewer reads it in one sitting, and a small change is easier for QA to check. Cutting thin doesn't always work out, but that's what we aim for.

    Do this in the same session as the grill: the agent already has the whole conversation in context and doesn't have to recall anything.

    1. Spec

    /mattpocock-skills:to-spec

    The agent assembles a spec from the conversation: problem, solution, user stories, decisions made, how to test. There's no new interview: the agent only confirms with you at which module boundaries to test the feature. The spec is published as a comment in PROJ-100.

    2. Tickets

    So the agent fills in the Jira fields right away, run to-tickets like this:

    /mattpocock-skills:to-tickets Create the tickets as children of PROJ-100. Set “Blocks” links by the graph. Fields: Project — <project>, Guild — Frontend, assign to me.

    The agent cuts the spec into vertical slices: each goes through all layers, can be verified on its own and fits in one session. It shows the list: check the ticket sizes and the links between them. Sometimes even a single slice is several thousand lines. Then ask for a thinner slice first: for example, one default color first, then the palette. After your “ok” the agent creates the tickets in Jira.

    PROJ-100. The agent proposed three slices. PROJ-101: the button on the booking page takes the accent color from settings. PROJ-102: the button text is readable on any palette color. PROJ-103: the client picks a color from the palette in settings. PROJ-101 blocks the other two.

    Done when: all tickets are in Jira, “Blocks” links are set.

    Prompt for a large ticket

    If a ticket looks large, ask to cut it:

    PROJ-103 will have a lot of code, it's hard for the reviewer to read. Use subagents to find thinner slices, each with its own visible result. If it doesn't cut thin, propose a stack by layers where every MR already has a consumer.

    Cutting by layers (API, model, UI) is the fallback. A layer without a consumer can't be judged by the reviewer, and the dead-code linter will fail. More about the stack in Slicing a branch into MRs.

    3

    Write the code

    You

    one session per ticket

    /implement
    Agent

    writes the code, runs the checks and compares the app with the mockup

    For every ticket we open a new session in the code repository: that way the agent starts with a clean context and thinks only about this ticket.

    /mattpocock-skills:implement We're working on PROJ-103 (the client picks a color from the palette). The spec is in PROJ-100. First re-read the ticket, the spec and the mockups, ask questions. Before making changes run the linter and tests to tell your errors from old ones. Research and independent blocks go to subagents. At the end open the app and compare it with the mockups.

    Don't skip the phrase “ask questions first”. Without it the skill starts writing code right away, and you won't get to correct its understanding of the task. The other phrases in the prompt matter too: the skill itself doesn't do a baseline and doesn't open the app.

    From there the agent works on its own. All you need to do is answer its questions and look at the result.

    PROJ-103. The agent asked whether to save the color immediately on selection or with a “Save” button, like the other settings. You chose the button. At the end the agent showed the output of tsc, eslint, jest and a screenshot of the app next to the mockup.

    Done when: checks are green, the app screenshot matches the mockup, the agent has shown the commands and their output.

    What the agent does

    The skill provides the skeleton: checks along the way and a review at the end. Our prompt adds the rest.

    1. Runs the linter and tests before making changes, to tell its errors from old ones.
    2. Writes the code, independent parts with parallel subagents.
    3. Runs tsc, eslint, jest on its own files until everything is green.
    4. Opens the app and compares a screenshot with the mockup.
    5. At the end reviews its own work with /code-review.

    What can't be checked (production build, CDN) the agent marks “not verified”. If you hear “it should work”, ask again.

    Commit

    The skill tells the agent to commit the work, but you make the commit: our agent rule overrides the skill's step. Look at git status before committing: the rule is written as text, not as a ban in the settings, and the agent can break it.

    A bug in the app

    If you found a bug in the app, run the diagnosis skill. The agent reproduces the bug, finds the cause and only then starts fixing:

    /mattpocock-skills:diagnosing-bugs <what is broken>

    If you need a live loop in the browser with debug logs:

    /segodnya-agents:local-debug @<file> <what is broken>

    Self-review

    You

    commit, Draft MR

    /checklist-deploy → /mr-ready
    Agent

    a fresh reviewer looks for everything a machine can find, and another agent fixes it, commits and pushes

    Before human review the MR goes through self-review: a fresh reviewer agent looks for everything a machine can find, and another agent fixes it. So the reviewer gets an MR where the machine-findable issues are already closed.

    1. Commit, push and create a Draft MR. The MR base is the branch the task branch was forked from.
    2. Build the deploy checklist from the diff against the MR base: 
      /checklist-deploy <MR base>
      The command fills in the description, test cases, environment changes and the rollback plan. Deploy notes, change type and the MR link (items 4, 6, 7) you add yourself. Post the checklist as a comment in the ticket: the mr-ready reviewer checks the diff against it, and QA tests the task by it.
    3. Open a new session in the code repository and run the self-review. Send two messages: first the goal, then the skill. The goal keeps the session from stopping in the middle of the loop. 
      /goal mr-ready has produced the final report on the MR. Deploy checklist: <Jira address>/browse/PROJ-103?focusedCommentId=<id>
      /segodnya-agents:mr-ready

    While mr-ready is running, almost nothing is needed from you. The skill asks you only if it hits a product fork: two UX options or an unclear backend contract.

    PROJ-103. The reviewer found that an empty color value breaks the button. The fixer added a default color, pushed a commit and replied in the thread with its hash. The second round had no findings, and the report came back with status ready.

    Done when: the mr-ready report is ready, CI is green. If the report is stuck or cap, read its “Open for the reviewer” block and decide yourself.

    What mr-ready does

    A fresh reviewer looks for problems in the diff and checks it against the checklist. It leaves every finding as a thread on the right line of the MR. Another agent fixes it or replies why no fix is needed, then commits and pushes. The loop repeats until the findings run out.

    mr-ready is the only skill our rules allow to commit, push and write to the MR without a separate request. --force, --amend, rebase and resolving threads are forbidden to it.

    The reviewer and the fixer are different subagents, and they're fresh in every round. A fix goes out as a commit with a reply in the thread, a rejection as a reply with reasoning. Threads are resolved by the human reviewer, not the agent. If the reviewer found a defect outside the task's diff, it goes into the report as a ticket draft.

    The skill asks questions in two cases: as a batch at the start, if something is missing (the checklist, the check commands), and at a product fork.

    When it stops and what to do if it got interrupted
    StatusWhen
    readyno findings
    stucka finding survived two fixes, a round repeated the previous one with no new commits, or two rounds in a row had only design notes left
    cap10th round
    blockedpush failed

    If the result isn't ready, the reason is in the first line of the report. If the session got interrupted, just run the skill again. Every run starts from scratch, but nothing is lost: the threads, replies and commits are already in GitLab and git.

    /segodnya-agents:mr-ready <MR link>

    Review

    You

    remove Draft

    Agent

    if the reviewer left comments, mr-ready takes the open threads, fixes or replies, and pushes

    The last step is handing the MR to a human. The reviewer should understand the change without a call.

    Remove Draft and check that the MR has:

    1. Title: the ticket key and name.
    2. Description: a link to the ticket with the checklist and the Summary / Self-review block from mr-ready.
    3. Self-review threads on the lines, each with a reply: a commit hash or the reason for rejecting. The reviewer resolves them right at the code, and the next mr-ready run doesn't raise rejected ones again.

    If the reviewer left comments, you don't need to work through them by hand. Run mr-ready again: the skill takes all open threads, its own and the reviewer's, fixes or replies, and pushes.

    /segodnya-agents:mr-ready <MR link>

    PROJ-103. The reviewer asked in a thread why the client can't pick any color. mr-ready replied with a link to ADR-0001. The reviewer resolved the thread and merged the MR.

    The task is delivered when the MR is merged and all threads are resolved.

    Slicing a finished branch into MRs

    Sometimes the decomposition fails and the whole feature grows in one big branch. This is the emergency exit: next time cut the task at step 2. But if it has already happened, the branch can be carefully sliced into several MRs.

    How to slice a branch into several MRs

    Our goal is to turn a verified branch into several small MRs without conflicts and without losing changes. Then each MR goes through step 4.

    1. Slicing plan

    Suggest topics to the agent and ask it to check the dependencies:

    The branch diff is big. I propose splitting it into N MRs: <topic 1> / <topic 2> / <topic 3>. Check the dependencies by imports: a stack, or independent of master? Will there be conflicts?

    The agent picks one of two shapes. Independent MRs each branch off master (or the feature's base branch) and merge in any order. That's only possible if the parts don't import each other. In a stack each MR targets the previous one's branch. It suits a shared foundation: a behavior-preserving refactor → data → UI. A stack is merged bottom-up, without squash, and after a merge GitLab retargets the next MR itself.

    The bottom of the stack must not contain code without consumers, such as a schema or a hook nobody calls. The reviewer won't understand what they're for, and the dead-code linter will fail. In that case a bigger MR is better.

    2. Slicing

    Now ask the agent to distribute the changes across branches:

    Create tickets for the new MRs as children of PROJ-100. Distribute the changes across branches with subagents, each in its own worktree. Check every branch (tsc, eslint, tests, e2e), commit, push, create the MR. Then verify: the top branch is byte-for-byte equal to the original.

    Branches are assembled from the final state of the files, not by slicing the commit history, so there are no conflicts. At the end be sure to verify: the command below must print an empty diff. If it isn't empty, some change got lost or duplicated.

    git diff <original branch> <top of the stack>

    Here the agent commits and pushes itself: you explicitly allow it for the duration of the slicing.

    3. Checklists

    What's left is the checklists:

    For each ticket — /checklist-deploy on its MR's diff, post it to the ticket in jira wiki markup. The overall QA checklist for the whole feature — in PROJ-100.

    A ticket's checklist has only the cases of its diff and the merge order under “Deploy notes”. The overall checklist describes end-to-end scenarios: QA uses it to test the feature as a whole once all MRs are merged.

    Then run /segodnya-agents:mr-ready on every MR, from the bottom of the stack up.

    Done when: all MRs are green in CI with no conflicts, the verification diff is empty, the checklists are posted.

    Protecting the context

    The agent's context is limited. In a long session the model makes worse use of what happened long ago (context rot). A 1M-token window postpones compaction but doesn't remove the problem. So we keep everything where the agent will fetch it on its own when needed. Five habits help with that:

    Hand recon to subagents

    They read many files and return only the output to the main session.

    /clear, not /compact

    …once everything decided is already in files. The /compact summary loses details, and a clean session with a good prompt almost always works better than a long one. /compact is needed only if there are unrecorded decisions left.

    Leaving? Leave a handoff

    /mattpocock-skills:handoff: the goal, decisions and reasons, what was tried and dropped, the next step. The note goes to a temporary folder and links to task.md and the tickets instead of copying them.

    Don't bloat CLAUDE.md

    A rule the agent follows even without it is redundant (“Bloated memory”). CLAUDE.md guides the agent but doesn't guarantee compliance. A critical ban is set via permissions.deny or a hook (“Executable guardrails”).

    Give the agent a way to verify itself

    A test, a linter, a screenshot next to the mockup. The proof comes from the environment, not from the agent's story (“Feedback loop”). Otherwise the agent declares premature success.

    Maintenance

    Junk piles up between sessions: outdated rules in CLAUDE.md, stale memories, MCP servers and plugins nobody uses. All of it loads into the context and pulls the agent the wrong way. Clean up from time to time. Six tools help with that:

    Session retro: /mattpocock-skills:retro

    The agent reads the session log and proposes changes to the environment, not to the code: a navigation pointer, a linter rule or a hook instead of a rule in CLAUDE.md, a new rule for the reviewer, removal of instructions that change nothing. Findings come sorted by severity. Only you can start the skill. Run it after a session where the agent went in circles or made a mistake a check could catch. The skill ships in mattpocock-skills 1.3.1 and later.

    Setup checkup: /doctor

    The alias is /checkup. Claude checks the installation (duplicates, PATH, broken settings, a new version), unused skills, MCP servers and plugins against their context cost, slow hooks, and CLAUDE.md content the agent can derive from the code. Claude applies fixes only after you confirm. claude doctor in the terminal gives read-only diagnostics without a session.

    Instruction audit: /doctor prompt-audit

    Claude looks for instructions written for older models, links to files and commands that no longer exist, and files that contradict each other. The audit covers CLAUDE.md, AGENTS.md, rules, skills, subagents and output styles in .claude/ and ~/.claude/. You get a report with proposed edits. Files change only when you ask. To audit one skill, pass its path: /doctor prompt-audit .claude/skills/deploy. Requires Claude Code v2.1.283 or later.

    Usage report: /insights

    Claude analyzes your recent sessions on this machine and writes an HTML report: what you work on, where things go wrong (misunderstood requests, buggy code), which features to try. One run covers up to 200 new sessions and spends tokens from your plan. The report stays in ~/.claude/usage-data/ for 30 days. A friction point from the report is a good candidate for retro.

    Memory review: /memory

    Claude saves notes for itself in ~/.claude/projects/<project>/memory/. The first 200 lines of the MEMORY.md index load into every session. Memory files never expire: a finished task or a dropped decision stays there until someone deletes it. /memory opens the folder and turns auto memory on or off. /context shows which files loaded at launch.

    Skill duplicates: /skills

    The same skill often lands twice: as a plugin and as a standalone copy in ~/.claude/skills/, for example after npx skills add. A plugin skill has a prefix (/mattpocock-skills:tdd), so both copies load. Their descriptions take double space in the skill listing, and the listing has a budget: on overflow Claude Code drops the descriptions of rarely used skills. The copies update separately and drift apart. A standalone code-review also replaces the bundled /code-review. /skills shows where each skill comes from, /skill-doctor shows its context cost and how often it runs. Keep one copy: delete the standalone one or turn the plugin off in /plugin.

    New repository setup

    This setup is done once per repository, not per developer. It's needed if the repository has no docs/agents/issue-tracker.md file.

    Why, who does it, 7 steps and the Jira text

    Matt's skills (to-spec, to-tickets, wayfinder) need to know where the tasks live and where the glossary and ADRs are. These settings are stored in the repository itself, so one person sets them up and commits them for the whole team.

    Any developer can do this. Just agree with the repository owners first: the change touches the shared CLAUDE.md.

    1. Go through step 0 in this repository.
    2. Run /mattpocock-skills:setup-matt-pocock-skills in Claude. The skill explores the repository and asks 1–3 questions.
    3. For the tracker question pick “Other” and paste the text below.
    4. If the skill asks about triage labels, decline: we don't use them in Jira.
    5. By default the skill looks for the glossary and ADRs in the repository root, but ours are per feature. So when the skill writes docs/agents/domain.md, ask it to replace the contents with our rule (text below).
    6. Check the diff: only the ## Agent skills block in CLAUDE.md and the docs/agents/*.md files should change.
    7. Submit the change as a regular MR.

    Tracker text (step 3)

    Tasks live in Jira (<Jira address>), we work through jira-cli.
Read: jira issue view <KEY> --plain. Create: jira issue create -p <PROJECT> --parent <KEY>,
body from a file: --template <file> --no-input < /dev/null. Fields: Guild — Frontend, assignee — me.
Blocking — the “Blocks” link (jira issue link). Publish the spec as a comment in the parent ticket.
We don't set triage labels.

    Rule for domain.md (step 5)

    Every feature has its own glossary (GLOSSARY.md or CONTEXT.md) and its own ADRs, they live in the feature folder in specs next to task.md. Read the ones that relate to the current task.

    Done when: the MR is merged, and /mattpocock-skills:to-tickets in this repository offers to create tickets in Jira.

    If the setup hasn't been done yet, work doesn't stop. Ask to-tickets to save the tickets as markdown files in the repository, then create them in Jira yourself or ask the agent to.

    Why Matt's skills

    There are many ready-made flows for agents. We compared five options and picked the one with the least ceremony for a typical frontend task.

    FlowHow it worksWhat's left after the taskCost for us
    Matt Pocock's skillsone short skill per step: grill → spec → tickets → code → reviewtickets in the tracker, a glossary, occasional ADRsour own skills are needed for MR self-review and Jira
    Superpowersa strict pipeline: brainstorm → design doc → a plan of 2–5 minute tasks → subagents, mandatory TDDa design doc and a plan for every featurea lot of ceremony for a hundred-line change; code written before the test gets deleted by the skill
    OpenSpecfor every change: proposal → tasks → implementation → archiveproposal.md, design.md, tasks.md and spec deltasa second source of truth next to arc/specs and Jira
    Spec Kitspec-driven development: project constitution → spec → plan → tasks → implementationthe most documents per featuredocuments have to be written, read and kept up to date
    Our own set of skillseverything tailored to uswhatever we decideonly we find and fix the bugs, a newcomer has nothing to read outside

    We chose Matt's skills for three reasons:

    1. One step, one skill, and a skill reads in a minute. For example, implement is a few lines. When the agent does something strange, the cause is easy to find.
    2. The skills have the conversation before the code, vertical slices and a reviewer in a separate session built in. The same techniques are described in Mokevnin's book and Anthropic's best practices.
    3. The project is alive: about 290K stars and 24K forks on GitHub, a release every one or two months. Updates arrive through the plugin, and re-running setup.sh breaks nothing.

    Matt's skills are written mostly by one author: the repository has 8 contributors. That's why the skills are consistent with each other. If a big developer community matters, Spec Kit has 321, OpenSpec 145, Superpowers 44. But they also have more documents per task. GitHub data as of October 16, 2026.

    Glossary

    If you came across an unfamiliar word in the text (agent, session, grill, spec, thread), look here. Terms with a dotted underline in the text show a tooltip on hover.

    Agent
    Claude Code: reads and changes code, runs commands.
    Session
    One conversation with the agent. A new session remembers nothing of the previous one except the files.
    Context (window)
    Everything the agent sees in a session: instructions, dialog, files it has read. It is limited. See Protecting the context.
    Subagent
    An agent the main session launches for a subtask. It has its own context and returns only its output.
    Skill
    A packaged instruction for a specific task. Invoked with the /name command.
    MCP
    A way to connect an external tool, such as a browser, to the agent.
    CLAUDE.md
    The rules file the agent reads at the start of every session: the personal ~/.claude/CLAUDE.md and the team one in the repository.
    One shot
    The agent does the task right away, without a preliminary conversation. Suits a tiny diff.
    Grill
    A mode where the agent asks questions until it fully understands the task.
    Wayfinder
    A decision map for a task that doesn't fit in one session. Every question is a separate ticket, resolved one at a time.
    Spec
    The outcome of the grill in one document: problem, solution, user stories, decisions, tests.
    Vertical slice
    A ticket that goes through all layers (data, API, UI, tests) and can be verified on its own. The opposite is an “API only” or “markup only” ticket.
    ADR
    A short record of an architectural decision: context, decision, reasons, consequences.
    Diff / staged
    Changes in the code / changes added to the git index (git add).
    MR
    Merge request in GitLab. A thread is a discussion on an MR line.
    Reviewer
    The developer who reviews the MR before merge.
    Baseline
    The state of the checks before changes. Helps tell your errors from old ones.
    Handoff
    A note for the next session: where you stopped and what to do next.
